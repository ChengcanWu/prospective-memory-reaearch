# LongMemEval-V2 笔记

> Wu et al., arXiv:2605.12493 — *LongMemEval-V2: Evaluating Long-Term Agent Memory Toward Experienced Colleagues*

## 1. 要解决的问题

现有 agent 记忆评测多盯用户聊天史、短轨迹，或只看下游任务是否成功，**很少直接测**：记忆系统能否从复杂定制环境里的长期交互中，内化成「资深同事」式的环境经验（界面差异、状态怎么变、工作流、常踩坑、错误前提）。

**核心问题**：如何评测 web agent 记忆是否把大量历史轨迹变成可复用的环境专属经验？

## 2. 方法流程（完整工作流）

LongMemEval-V2（LME-V2）把目标定为：优质记忆应让 agent 成为**特定环境里的经验丰富同事**。基准从 WebArena / WorkArena 类网站轨迹中人工出题，用「先灌历史轨迹、再取证问答」的接口评记忆系统，并给出两套 AgentRunbook 基线。

---

### 阶段 A：五种核心记忆能力

1. **静态状态回忆（Static）**：页面布局、模块能力、状态间细微差别等「地标」。  
2. **动态状态追踪（Dynamic）**：给定状态与动作，理解环境如何变化（世界模型式）。  
3. **工作流知识（Workflow）**：定制环境里常见任务的步骤套路。  
4. **环境坑点（Gotchas）**：反复出现的环境特异失败模式。  
5. **前提觉察（Premise）**：识别「换一个环境成立、在本环境不成立」的假设（含弃答类题）。

---

### 阶段 B：基准如何构建（四步标注）

#### B1. 轨迹收集

环境来自 WebArena（购物、CMS、论坛等）与 WorkArena / WorkArena++（如 ServiceNow）。用 AgentLab 统一状态/动作与 ReAct 式基座 agent，配合 Codex 等做拒绝采样。最终池约 **599** 条 WebArena + **941** 条 WorkArena 轨迹；整体成功率约 **52%**，平均每条约 **28.1** 个状态。

#### B2. 人工出题

专家按能力分类检查轨迹，写出「资深同事会自然记住」的问题；过滤掉前沿闭源模型仅靠参数知识就能答对的题（人工抽测多模型，要求至少两家答错）。Gotchas 常做成「新人发来带截图的消息」场景；其余为真假、选择题或短答。再基于静态/动态/工作流题构造**错误前提的弃答题**。最终 **451** 题；平均约需 **1.4** 条支撑轨迹（最多 5），但动态/工作流题常需轨迹内多状态综合。

#### B3. 答案轨迹标注

先为每题标种子答案轨迹；再扩展标注所有含答案的轨迹（Codex 提案 + 人工核验核心干草堆），便于后面拼共享历史。

#### B4. 干草堆（Haystack）组装

程序化生成两档历史：

| 档位 | 轨迹规模 | 量级（约） |
|------|----------|------------|
| LME-V2-Small | 全题共享约 **100** 条 | ~**25M** tokens，约 2.5K 状态 |
| LME-V2-Medium | 每题约 **500** 条 | ~**115M** tokens，约 14.9K 状态 |

干草堆平衡成功/失败轨迹；不少题**只能从失败轨迹**取证。答案相关轨迹在堆里仍稀疏（针在草堆中）。相较对话记忆基准，历史长 1–2 个数量级，且轨迹为**多模态**（文本+界面观察）。

---

### 阶段 C：评测协议（Context Gathering）

记忆系统需实现两个 API：

1. **Insert(h)**：消费一条轨迹；  
2. **Query(q)**：对问题返回紧凑多模态记忆上下文。

对每道题：按顺序把对应干草堆轨迹全部 Insert → Query 取上下文 → **截断到固定 token 预算（约 200K）** → 交给**固定阅读器 LLM**答题。报告**答案准确率**与**查询延迟**。结构化答案用归一化字符串匹配；自由答用 LLM 裁判。

这样直接评「记忆质量」，接口贴近下游 agent 真正会用的取证方式。

---

### 阶段 D：试点验证（说明题是否靠谱）

- **无历史只给题**：最强前沿模型整体约 **14.1%**，说明几乎不能靠公开/参数知识。  
- **oracle 只给答案轨迹**：长上下文直读仍受限；给证据切片+策略笔记可到约 82–86%；用 Codex 对轨迹文件多步查证据可到约 **89.7%**。说明标注基本可靠，且「编码 agent 当记忆控制器」有潜力。

---

### 阶段 E：基线方法 AgentRunbook

#### E1. AgentRunbook-R（偏效率的结构化 RAG）

**写入时**为每条轨迹建三个知识池：

- **原始状态切片池**：以状态为中心的局部 UI 观察与邻近动作（细粒度视觉/文本证据）；  
- **状态转移事件池**：相邻状态间动作如何改环境（世界模型证据）；  
- **流程与提示笔记池**：轨迹级工作流、导航模式、坑点（高层可复用知识）。

**查询时** LLM 控制器看问题与记忆快照，向各池发检索查询（可跳过无关池）：多路原始切片查询、一路事件、一路笔记；稠密检索后渲染为多模态上下文。延迟低，覆盖多能力，但细证据选择偏简单。

#### E2. AgentRunbook-C（偏准确的编码 agent 记忆）

写入：轨迹**原样落盘为文件**。  
查询：搭沙箱，注入三类脚手架——

1. **工作流文档**：要求 agent「当记忆模块」按步骤取证；  
2. **查询时清单（manifest）**：概括当前记忆布局，先短名单再细看；  
3. **辅助脚本**：按状态区间查看、轨迹内搜索等。

编码 agent 输出结构化检索结果（短记忆笔记 + 选中的状态跨度），再渲染成阅读器上下文。

主实验阅读器固定 Qwen3.5-9B；RAG 系用同模型作控制器 + Qwen3-Embedding-8B；编码系用 Codex + GPT-5.4-mini 等。

## 3. 达到的效果

- **无检索近零**；简单 query→切片 RAG：Small / Medium 约 **42.8% / 38.1%**；加笔记约 **51.0% / 45.9%**。  
- **AgentRunbook-R**：约 **58.6% / 57.0%**（整体约 **57.8%** 量级），明显优于朴素 RAG；消融表明切片池对静态题、事件池对静态/动态/坑点重要。  
- **现成 Codex**：约 **69.3%**，但查询约 **182 s**，约为 R 系约 **6.9×** 慢。  
- **AgentRunbook-C**：整体最佳约 **72.5%**（Small **74.9%** / Medium **70.1%**），查询比 vanilla Codex 约快 **32%**，推进准确率–延迟帕累托前沿，但仍有很大改进空间。  
- **定位**：面向「跨大量轨迹的环境经验记忆」的挑战性测试床（深度可达约 25M–115M tokens）。
